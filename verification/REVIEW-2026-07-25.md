# Database review — 2026-07-25

An independent review of the data model, the verification stores, the derived artifacts, and the
open issue backlog (#3, #5–#11). Findings are ordered by severity and mapped onto the existing
epic so they slot into the planned sequence rather than competing with it.

Every finding in this document is reproducible:

```
python verification/review_findings.py
```

That harness is the deliverable, not this prose. It encodes each finding as a named check that
fails today and passes once fixed, so the next agent can close the loop without re-deriving the
analysis. It is pure-Python, dependency-free, and needs no network or PowerShell, so it can run in
the #11 release gate on a stock runner.

## Method

Findings were produced by an iterative loop: form a hypothesis about an invariant, express it as an
executable check, run it, then inspect the generator source to decide whether a failure is a defect
or intended behaviour. Two hypotheses were **refuted** this way and are recorded here so they are
not re-investigated:

- *"The embedded `finishAvailability` in `snorlax_cards.json` is a stale snapshot."* It is not.
  `snorlax_cards.json` and `finish_units.json` were regenerated in the same commit (`1ea43b3`).
  `scripts/finishes.py:639` deliberately filters printings to those mapped to the current
  Cardmarket V-token, so the projection is *scoped*, not stale. The real defect is narrower and is
  recorded as F1/F2 below.
- *"Repository history carries secrets, personal paths, or PII"* (the #5 release blocker). It does
  not, on the evidence available: no absolute Windows/Unix user paths, credentials, cookies, or
  bearer tokens in any tracked `.ps1`/`.py`/`.md`/`.json`; no files deleted anywhere in history; a
  single committer using a GitHub `noreply` address. #5's audit still needs to cover the 198 card
  images and consent for owner attestations, which a text scan cannot settle.

## What is in good shape

This is a genuinely well-built dataset, and the review should say so plainly before it lists
defects. Verified independently rather than taken from the documentation:

- **Referential integrity is clean.** Zero duplicate `unitId`, `finishUnitId`, or `printingId`;
  zero orphaned units; zero natural-key collisions in either state store; all 198 image references
  resolve to files on disk with no orphans; `meta.verification` matches `units.json` exactly.
- **Evidence discipline holds.** All 705 resolved language units carry a non-trivial evidence
  string and a `sourceType`; all confirmed printings cite at least one source. The positive-evidence
  policy is applied consistently — `availableFinishes` agrees with `finishStatus` in all 637 finish
  units with no exceptions.
- **The hard modelling calls are right.** Separating `finish` / `foilPattern` / `markings` /
  `distribution` / `cardSize` is the correct decomposition, and the `reverse-holo-treatment` vs
  `distribution-promo` stamp-role split is a genuinely subtle distinction handled well. Keeping
  finish units keyed on (set, number, language) rather than on the opaque V-token is also correct.
- **The documentation is honest about its own limits.** The `XY-P 149` false-contradiction
  post-mortem and the "never contradict on bare absence" rule in `RESUME.md` are the kind of thing
  most projects quietly delete after fixing.

The defects below are concentrated in one place: the **projection layer** between the verification
stores and the artifacts consumers read. The stores themselves are sound.

## F1 — Confirmed finish evidence is dropped from every generated artifact

**Severity: high. Blocks #8, and silently corrupts #9 and #10 if built on the current projection.**

`scripts/finishes.py:639` projects a finish unit onto a card by keeping only printings whose
`mappedVariants` contains that card's V-token:

```python
mapped = [printing for printing in unit["printings"] if token in printing["mappedVariants"]]
```

A printing mapped to **no** variant therefore reaches no consumer at all. There are **27 such
printings, every one of them externally confirmed** — including `SM 05` non-holo in all six Western
languages, `SSH 142` holo in five, `SVP 184` holo in five, `PGO 055` holo in five, `VIV 131` holo in
five, and the `CL 33` prerelease-staff holo. They exist in `finish_units.json`, and they appear in
`snorlax_cards.json`, `analysis_confirmed_releases.json`, and `confirmed-releases.html` nowhere.

The visible consequence is worse than an omission: **53 cells in the published table render blank**
where the store holds positive evidence — `RR 33 V2` French/German/Italian, `CL 33 V2` French, and
others. A blank cell reads as "nothing is known about this printing", which is precisely the claim
the project's positive-evidence policy exists to avoid making.

This is a projection bug, not a data bug. The store is correct; the view discards from it.

Neither existing check catches this. `review_integrity.ps1` check 145 validates that mappings
*point at* local products; nothing validates that printings are *covered by* a mapping. Check 179
asserts only that every card carries a finish summary, not that the summary agrees with the store.

**Why this blocks #8.** #8's own baseline — "691 entries backed by logical physical-printing
records" — is computed from `finish_units.json`, which has exactly 691 printings. But the rendering
path in use today reads the projected view. If the checklist generator follows the existing pattern,
27 confirmed printings vanish from the canonical export, and #8's acceptance criterion "expand by
logical `printings[]`, not group-level boolean finish flags alone" is silently violated. Fix the
projection before defining the canonical export, not after.

**Recommendation.** Decide explicitly which question each artifact answers, then enforce it:
carry unmapped printings into the projection under an explicit `mappedVariants: []` /
`productMapping: "unresolved"` marker rather than dropping them, and add a coverage assertion —
every confirmed printing must be reachable from at least one product view — to both
`review_integrity.ps1` and the #11 gate. Checks `F1.1`–`F1.3` in the harness encode this.

## F2 — `pending` conflates "no evidence" with "not attributable to this product"

**Severity: high. Blocks #8; affects #7 and #10.**

In `finish_units.json`, `pending` has one carefully documented meaning: no positive evidence has
been established. In the projected card view it acquires a second, undocumented meaning: evidence
exists at set-number-language level but is not attributable to *this* Cardmarket product. **110
card-language-finish cells** are weaker in the projection than in the store for this reason, and the
projected row carries no field explaining which kind of `pending` it is — `productMappingStatus`
exists on the finish unit but is not propagated into `byLanguage`.

README line 55 makes this actively misleading by presenting the two layers as interchangeable:

> Use `finishAvailability` on each card **or** the authoritative `verification/finish_units.json`.

They answer different questions and disagree in 110 places. A consumer who follows that sentence
sees `pending` and applies the documented meaning — "not established" — to facts the project has
already established. That undercuts the discipline the whole verification layer is built on.

**Recommendation.** Propagate `productMappingStatus` into every projected row and give the two
states distinct names in the public vocabulary (for example `pending` vs `unmapped`). Amend README
line 55 to state which question each layer answers. Do this before #7 writes the public
methodology section and before #8 freezes the checklist vocabulary — both will otherwise inherit
the ambiguity into published prose.

## F3 — README states three generated facts incorrectly

**Severity: medium-high. Cheap to fix, currently public-facing, and #7 defers it behind blockers.**

| README claim | Generated data |
|---|---|
| Non-holo: **276** units | **270** (`analysis_finishes.json`) |
| Both non-holo and holo: **24** units | **18** |
| "`JTG 117` now explicitly shows **non-holo, holo,** and intricate-tile reverse-holo" | **holo + reverse-holo only** |

The JTG error is the significant one. `review_integrity.ps1` check 173 already enforces "regular
JTG 117 discloses holo + reverse only", so the test suite and the README currently assert opposite
things about the same card. The non-holo printing belongs to the Prize Pack product (`PPS8`), not
the regular card — exactly the confusion #8 lists as a required regression case.

Both count errors entered in `1ea43b3`, the same commit that regenerated the data: the prose was
hand-updated to values that match neither the old nor the new generated output.

#3 and #7 both note this, but only as a prerequisite buried inside a large frontend issue that is
blocked by #5 and #6. The README is the project's public face *today*. It should be corrected now
and, better, generated: the finish table is derivable from `analysis_finishes.json`, so the fix
should remove the hand-maintained numbers rather than re-typing them.

## F4 — The main dataset still advertises languages the project has refuted

**Severity: medium. Affects #7 and #8.**

The project's headline finding is that Cardmarket's language filter over-claims — 71 contradictions,
with `KSS 26` advertised in 17 languages and printed in 7. Yet `snorlax_cards.json` still carries
every refuted claim in `cards[].languages`, and **36 of 191 non-code-card products** list at least
one language this project has itself disproved. There is no `languagesConfirmed` /
`languagesContradicted` field; the refutation lives only in `verification/units.json` and
`CONTRADICTED.json`.

A consumer reading the main dataset — which README describes as the **main dataset** — gets the
unfiltered marketplace claim. The caveat is documented in prose, but prose does not survive a
`json.load`.

`analysis_confirmed_releases.json` already solves this correctly with its `confirmedLanguages`
field, so the pattern exists and needs only to be applied upstream. Doing so before #8 also removes
a class of error from the checklist expansion, whose first rule is "start only from confirmed
card-language units".

## F5/F6/F7 — No canonical identity or typed fields for the public artifacts

**Severity: medium. Direct prerequisites for #8 and #10.**

Three related gaps in the same layer, best fixed as one normalization pass:

**F5 — no stable row identity.** `correction_issue_url(r, row_number, ...)` embeds
`Generated row: {row_number}` and the `aria-label` uses the loop index. #10 requires "stable row
identity used by correction and checklist features" and "Correction links remain attached to the
correct stable row" after sorting — neither is achievable while identity *is* the sort position.
The natural key `(setCode, number, variant, edition)` is already unique across all 203 rows with
zero collisions, so a stable `rowId` can be materialized today at no modelling cost. This is
currently unscoped: #10 lists it as an acceptance criterion, but no issue owns producing it as data.

**F6 — inconsistent null representation.** Unnumbered products (`PJU`, `G2`, `EXS`, `DP1`, `UNP`)
are `null` in `snorlax_cards.json` and `units.json` but `""` in `finish_units.json`. Every join site
already compensates with `str(x or "")` — `finishes.py:637`, `confirmed_releases.py:25`, and the
harness itself. A null cannot participate in a stable checklist ID (#8) or a natural-number sort
(#10), so this must be settled before either.

**F7 — untyped, inconsistently flagged dates.** `date` mixes `YYYY` (45 rows), `YYYY-MM` (44) and
`YYYY-MM-DD` (114) in one string field, with no normalized sort key. Worse, `dateExact` is applied
inconsistently to identical precision: 10 month-precision rows are flagged `true` while 34 are
flagged `false`, against a documented rule that `false` means year-level. #10 requires "typed
release sorting using underlying dates while retaining approximate-date display" and "approximate
release dates sort consistently"; both need a normalized `dateSort` plus a coherent precision
field (`year` / `month` / `day`) rather than a boolean carrying two meanings.

## F8 — The integrity suite is a snapshot test, not an invariant suite

**Severity: low-medium. Shapes #11.**

`review_integrity.ps1` hardcodes the current state as the expected state: `719 units total`,
`637 finish units`, `artist coverage 115/198`, `9 pending`, `5 manual review, all Portuguese`.
These are not invariants — they are a snapshot. Closing a single open unit, which is the project's
declared next action (#2 and #3 in HANDOVER §8), turns the suite red and pressures the engineer to
edit the assertion to match. A suite that must be edited on every successful piece of work stops
being trusted, and it will not tell you which of the two changed for the right reason.

The structural checks in the same file are genuinely good and worth keeping. The fix is to separate
them: assert *invariants* (uniqueness, referential integrity, evidence presence, taxonomy validity,
status-sum consistency) as failures, and *report* counts as drift without failing. `verification/
review_findings.py` demonstrates the split with its `INFO` severity.

This matters for #11, whose release gate inherits the suite. As specified, the gate would block
deployment whenever verification progress lands — the opposite of the intended behaviour.

Secondary note for #11: the entire recurring verification suite is PowerShell, so the gate needs
`pwsh` on the runner (available on `ubuntu-latest`, but an explicit dependency worth stating) and a
decision on whether new checks are written in PowerShell or Python. The review harness is Python
specifically so the gate has a portable floor.

identity, *then* define the canonical checklist export on top of it.

## Outcome

All six findings were implemented, followed by the epic issues #5–#11. The harness grew from 17
checks to 41 as each acceptance criterion became executable, and `verification/test_site.py` adds
31 browser checks against the real page.

What the loop caught that review alone did not:

- **The first diagnosis was wrong.** The projected finish view looked like a stale snapshot — 110
  fields all weaker than the store, one-directional, a textbook staleness signature. Git history
  showed both files regenerated in the same commit, and the generator showed the filtering was
  deliberate. Filing the first diagnosis would have sent someone chasing a regeneration bug that
  does not exist. The real defect (F1/F2) is narrower and different.
- **Strict provider matching found five undeclared providers** (#6), including the Play! Pokémon
  rewards gallery — one of only two sources here permitted to establish an absence. A permissive
  "other" bucket would have hidden it.
- **Checklist ID generation collided on xJTG 117** (#8), whose three Cosmos-holo printings differ
  only by retailer stamp. The ID keyed on marking *role* rather than the text printed on the card,
  so the exact regression the issue names was about to be merged into one item.
- **The edition rule diverged from `confirmed_releases.py`** (#8), which would have labelled 780
  items "Unlimited" while the chronological table called the same cards "—".
- **Browser tests found four defects static review missed** (#7/#9/#10): the collection table
  overflowing both paper sizes in print, sort indicators rendering as the literal text `\2195`
  from a double-escaped CSS string, 34 columns wrapping cells into 173px rows, and a checklist
  scope test that passed without ever applying a filter.
- **The release gate found two page generators writing the same file** (#11) — the duplicate
  implementation #7 exists to prevent — as a determinism failure.

One check fails deliberately: `L1`, the verbatim licence texts. The environment's network policy
denies `polyformproject.org` and `creativecommons.org`, and reconstructing a legal text from
memory risks silent divergence from the published wording. `LICENSES/README.md` carries the fetch
commands, and the gate refuses to publish until both files exist.
